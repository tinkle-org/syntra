## 1. Profile status and optionality

The profile is OPTIONAL on the wire, capability-gated, and additive ([RFC 0006 §11.1](../../rfcs/0006-update-recovery-profile.md#11-decision-amendment--release-inclusion-and-recovery-safety)).

Release inclusion and wire optionality are separate decisions:

- Release bundle: standardized recovery is REQUIRED in the target v1 release bundle. A release presented as meeting that target includes this accepted contract, matching schema documentation, and independent Rust/Go acceptance evidence for its initiator and host roles. Recovery cannot be omitted from that release and relabeled as an optional future implementation item. Core-only conformance cannot satisfy the bundle: recovery inclusion is a release obligation, not a condition of a Core-only claim, and a Core-only success is insufficient evidence for the recovery-inclusive release target.
- Wire per connection: the capability identifier `syntra.update-recovery/1` remains optional and explicitly negotiated after ACTIVE, independently on every connection. No unsolicited profile traffic, handshake extension, new `Frame` variant, or implicit continuity is introduced. A release participant still interoperates with Core-only peers using mandatory-only behavior; where the capability is negotiated and confirmed, negotiated fallback outside the recovery-inclusive release target is recorded as supplying no recovery guarantee.

A minimal implementation supporting only handshake, generic invocation, cancellation, and typed errors interoperates with a profile-confirming peer at mandatory-only behavior with no recovery contract. Negotiation uses a standardized generic invocation after ACTIVE. Confirmation is per connection. Confirmation on one connection does not enable the profile on another. Partial acceptance falls back to mandatory-only operation plus any previously confirmed options.

Unnegotiated use fails. A host that does not confirm the profile rejects profile invocations while continuing mandatory service. An initiator that does not offer the profile never receives profile batches. Downgrade is explicit confirmation, never probing.

No `Frame` variant is added, deprecated, or renumbered. All versioned profile payloads travel inside existing `RpcRequest` payload, `RpcResult` payload, or `Notification` payload bytes. Reserved numbers 16, 17 and reserved names `event`, `resume`, `ack` in the [envelope schema](../../proto/syntra/v1/envelope.proto) are preserved unchanged and are not reused by this profile. Profile versioning lives inside the opaque payload bytes, not in `Frame.version`.

Standardized generic RPC methods are canonical `/package.Service/Method` paths with exactly two slashes per `SNTR-RPC-001`:

- `/syntra.v1.UpdateRecovery/Negotiate` — `RecoveryNegotiateRequest` / `RecoveryNegotiateResponse`
- `/syntra.v1.UpdateRecovery/Subscribe` — `RecoverySubscribeRequest` / `RecoverySubscribeResponse` (per-round handle H and fixed boundary B)
- `/syntra.v1.UpdateRecovery/Replay` — `RecoveryReplayRequest` / exactly one `RecoveryReplayPage` per `RpcResult`
- `/syntra.v1.UpdateRecovery/CatchUp` — `RecoveryCatchUpRequest` / `RecoveryCatchUpAccepted` in terminal `RpcResult`
- `/syntra.v1.UpdateRecovery/Confirm` — batch `RecoveryConfirmRequest` / `RecoveryConfirmResponse`
- `/syntra.v1.UpdateRecovery/SnapshotConfirm` — snapshot-boundary `RecoverySnapshotConfirmRequest` / `RecoverySnapshotInstalled`
- `/syntra.v1.UpdateRecovery/SnapshotOffer` — `RecoverySnapshotOfferRequest` / `RecoverySnapshotDescriptor`
- `/syntra.v1.UpdateRecovery/SnapshotFetch` — `RecoverySnapshotFetchRequest` / exactly one `RecoverySnapshotChunk` per `RpcResult`; transfer completion is derived locally from index coverage and byte accounting; the protocol defines no wire transmission for `RecoverySnapshotComplete`
- `/syntra.v1.UpdateRecovery/Unsubscribe` — `RecoveryUnsubscribeRequest` / `RecoveryUnsubscribeResponse`

Every profile `Notification.payload` carries exactly one versioned `RecoveryNotification` discriminator (`batch` | `replay_complete` | `trailer` with matching `profile_version`) with no envelope changes. Replay pages are never page `Notification`s: each Replay call returns exactly one page in its correlated `RpcResult` (§5). Malformed method paths MUST be rejected with `INVALID_ARGUMENT` before dispatch. All IDL types are defined in [recovery_profile.proto](../../proto/syntra/v1/recovery_profile.proto).

Snapshot semantics follow RFC 0006 §11.5: installation is application-local and same-generation, the descriptor binds the offer to `(P, S, H, G, S0)`, and no `RecoverySnapshotComplete` wire carrier exists. Batch and snapshot confirmation use distinct methods so compatible Protobuf field shapes cannot confuse their intent. Generated codec freshness establishes representation only; idempotent-retry eligibility, issued-checkpoint validation, and other runtime rules in §6 and §7 remain implementation obligations.

Ownership: Syntra owns framing, session and invocation machinery, envelope correlation, capability mechanics, and transport carriage. Authentication, authorization policy, method schemas, replay storage, snapshot content, presence, and durable data remain host-owned above Syntra. Connection liveness, authentication validity, committed progress, and durable acknowledgement stay distinct concerns.

All examples in this document are neutral only: echo round trip, generic key/value read, generic subscription establishment. They illustrate mechanics and impose no data model.

## 2. Requirement IDs

IDs in this section use prefix `SYN-URP`. They are accepted requirements of RFC 0006 as amended by §11. Core `SNTR-*` IDs remain owned by their defining core documents listed in [core index](../core/README.md) and indexed in [requirement registry](../core/requirements.md). `SYN-URP-008` and `SYN-URP-009` are reserved and not assigned.

### 2.1 Initiator obligations

**SYN-URP-001** — The initiator MUST NOT use any profile operation, except the standardized profile negotiation invocation after ACTIVE, before the profile capability is confirmed for the connection. The initiator MUST negotiate the profile after ACTIVE through the standardized generic invocation defined by the profile, MUST handle partial acceptance by falling back to mandatory-only operation plus any previously confirmed options, and MUST NOT send profile payloads for an unconfirmed capability. The negotiation invocation itself is the only permitted profile operation before confirmation. Release-bundle obligations under RFC 0006 §11.1 do not relax this per-connection gate: every use of the profile on a connection is negotiated on that connection.

**SYN-URP-002** — The initiator MUST treat every profile payload as versioned bytes carried inside existing `RpcRequest` payload, `RpcResult` payload, or `Notification` payload. The initiator MUST NOT require any new `Frame` body variant, field number, or field name, and MUST preserve and respect reserved numbers 16, 17 and reserved names `event`, `resume`, `ack`.

**SYN-URP-003** — The initiator MUST treat each subscription as one delivery instance running on a stable stream identity S resolved by the provider from the selector within an authenticated principal scope P. Several subscriptions MAY observe the same S with independently maintained queues and phases. The initiator MUST track one continuity generation G per subscription, MUST treat checkpoints C as opaque bytes bound to `(P, S, G)`, MUST persist the binding context with C without parsing C, MUST present exact checkpoint bytes with explicit predecessor/result pairing, and MUST NOT perform arithmetic on checkpoint bytes (no increment, decrement, ordering inference, or structural parsing) and MUST NOT infer scope or authority from selector-byte equality.

**SYN-URP-004** — The initiator MUST begin every recovery round by subscribing and MUST carry the round under the fresh connection-scoped handle H and the non-empty fixed boundary B captured at that accept. Equality of boundary bytes never identifies a round; the pair `connection + H` does. The initiator MUST consume bounded replay page units delivered in their correlated `RpcResult` per SYN-URP-014, MUST follow the page continuation marker, MUST stop at B, MUST apply the same validation pipeline to recovered batches and live batches, and MUST tolerate a duplicate result checkpoint only after version, handle/scope, generation, authorization, and bounds validation; equal bytes from another connection, handle, generation, or principal context are not a duplicate. The initiator MUST NOT release held live batches before a validated completion matching its current connection, H, generation, profile version, and exact B (SYN-URP-023).

**SYN-URP-005** — The initiator MUST follow the commit sequence receive → validate → offer → persist → confirm, where persist covers the application effects represented by the checkpoint and not merely its opaque bytes: the application either atomically persists those effects and `(P, S, G, C)`, or supplies an idempotent recovery fence that durably identifies the operation and reconciles or reapplies it safely across every crash window. A checkpoint ahead of durable application state is unsafe. The application MUST declare its durable success point and fence contract; offer return, asynchronous write submission, decode, and transport receipt are NOT that point. Transport receipt or envelope decode MUST NOT be reported as committed progress or as application success. Unsupported persistence semantics cannot claim recovery safety.

**SYN-URP-006** — The initiator MUST route each received batch to exactly the delivery instance whose opaque handle it accompanies, MUST keep connection state separate from per-instance state, and MUST tear down only the targeted subscription on a per-stream terminal signal. Reconnection ALWAYS establishes a new authenticated connection, negotiates again, and subscribes to a fresh handle H with a newly captured boundary B; it transfers neither capability state nor pagination or snapshot handles. The initiator MUST carry forward only its durable known-safe checkpoint C (SYN-URP-005) bound to the same `(P, S)` where host validation permits, and MUST track three distinct observations locally — locally durable C, Confirm sent for C, and peer-acknowledged C — never collapsing them.

**SYN-URP-007** — The initiator MUST enforce its bounds (pending invocations, subscriptions, queued bytes, page sizes), MUST back off on `RESOURCE_EXHAUSTED`, and MUST NOT silently accept truncated history as complete. Subscriber-local saturation is subscriber-local: on local overflow the initiator MUST end the affected subscription or report an explicit local recovery-needed event, clear its held queue and cursors, retire the handle H, and begin a fresh round through a new Subscribe (SYN-URP-006, SYN-URP-024). It MUST NOT increment or fabricate a provider generation, invert a local failure into a shared `next_generation`, or invalidate another subscriber's checkpoint by its local overflow.

### 2.2 Host obligations

**SYN-URP-010** — The host MUST confirm the profile only where it implements it for the bound principal, MUST confirm per connection so that confirmation on one connection does not enable the profile on another, MUST document the confirmed profile version and bounds per deployment, MUST accept the standardized profile negotiation invocation after ACTIVE before confirmation where the host implements the profile, and MUST reject other unnegotiated profile use with `UNIMPLEMENTED` (an operation that is unknown, or that belongs to a profile not confirmed on this connection) or `FAILED_PRECONDITION` (use of an unconfirmed option on a connection that has confirmed the profile). The negotiation invocation itself is the only permitted profile operation before confirmation. Release-bundle inclusion under RFC 0006 §11.1 does not change per-connection confirmation or refusal behavior.

**SYN-URP-011** — The host MUST implement negotiation, subscribe, replay, catch-up, snapshot, continuation, confirm, and terminate operations as standardized generic invocations with versioned payloads inside existing envelopes. The host MUST NOT add envelope fields, MUST NOT reuse reserved numbers 16, 17 or reserved names `event`, `resume`, `ack`, MUST NOT introduce a wire carrier for `RecoverySnapshotComplete` (SYN-URP-016), and MUST keep unknown profile fields ignored on receipt where explicitly marked ignorable, rejecting unknown profile operations with `UNIMPLEMENTED`.

**SYN-URP-012** — The host MUST maintain the provider-resolved scope `(P, S)` for each subscription and MUST bind every checkpoint C to exactly one `(P, S, G)` triple, where G is the provider's continuity generation for that scope. Generation change represents true provider history loss or an explicit shared rebase within that scope and ONLY that: it MUST NOT result from subscriber-local saturation, ordinary retention-window pruning, or targeted revocation termination without policy-driven history reset (SYN-URP-026). A generation change invalidates all earlier-generation checkpoints in that scope, including those held by other subscriptions; the host MUST fence their outstanding pages, offers, confirmations, and batches and signal the invalidation explicitly with a trailer whose `generation` is the old G and whose `next_generation` is the new G. If the signaling is lost, the next old-generation operation MUST fail with `FAILED_PRECONDITION`; stale bytes never acquire the new meaning silently. A provider loss spanning several principal scopes invalidates every affected scope explicitly. A checkpoint outside a replay retention window does not by itself invalidate the binding or increment G; it requires explicit snapshot fallback (SYN-URP-015). Identical selectors do not establish identical scope or authority.

**SYN-URP-013** — Each batch MUST state the predecessor checkpoint it continues from and the result checkpoint it advances to. The host MUST NOT require the initiator to compute a successor, and MUST NOT perform arithmetic on checkpoint bytes. Before exposing any committable batch result or snapshot boundary the host/provider MUST establish a recoverable issued binding of those bytes to `(P, S, G)` that does not depend on Confirm receipt or per-handle reply caching; whether the binding is durable or reconstructible provider state is a host obligation, and its loss requires explicit failure and recovery, never the assumption that a lost acknowledgement proves no local commit occurred or the invention of a new generation. Host validation of an issued checkpoint is distinct from accepting an unoffered Confirm on an active handle: batch Confirm still requires a committable batch result issued for that handle and generation, and SnapshotConfirm requires the current offered boundary; subject to those preconditions the host MAY accept valid C without a previous confirmation record. The host MUST reject forged, malformed, cross-stream, cross-generation, or cross-principal checkpoint bytes with `FAILED_PRECONDITION`, or `UNAUTHENTICATED` where token-like, without leaking other principals' stream state.

**SYN-URP-014** — The host MUST return exactly one `RecoveryReplayPage` in the correlated `RpcResult` of each Replay invocation, each page stating its continuation marker and the round's fixed boundary B. Replay pages are never delivered as page `Notification`s. Oversized history MUST be paged across several bounded invocations, never burst beyond the documented per-connection and per-subscription queue bounds. Invocation-triggered catch-up streams over the existing connection as `Notification` batches through the same validation and authorization path as live batches. The host MUST NOT advance B during a round, MUST treat a round's completion fences as identified by `connection + H`, and later-handled retired-handle pages, completions, RPC results, and batches have no effect even when their boundary bytes equal the current B (SYN-URP-023). The host MUST re-emit a retained page or round completion, verbatim and without pagination or application advancement, on a bounded exact duplicate retry in the current round (SYN-URP-022).

**SYN-URP-015** — The host MUST emit an explicit catch-up completion signal when the stream reaches live, and MUST fail the failing replay/catch-up invocation with `FAILED_PRECONDITION` in `RpcResult` while emitting an explicit snapshot-required signal as `RecoveryBatchTrailer{snapshot_required=true}` in a `Notification` payload when the requested checkpoint is outside retention or otherwise unrecoverable by replay. A retention-window miss does not increment G or invalidate otherwise valid checkpoints; it requires the snapshot fallback. Silent restart from an unrelated point is forbidden. Silent truncation without the documented signal is forbidden.

**SYN-URP-016** — The host MUST implement the snapshot transfer and local-installation contract through generic invocations in bounded pages. `SnapshotOffer` returns `RecoverySnapshotDescriptor` bound by the host to `(P, S, H, G, S0)`: handle H, snapshot handle X, provider-proven boundary S0, page count N, and page byte bound; the descriptor has no generation field and G is the subscription's established generation. At most one distinct X is offered under H; an exact duplicate `SnapshotOffer` under the active H returns the retained descriptor rather than a second offer, and superseding an offer retires H and requires a fresh Subscribe before a new X is issued, even when the new boundary equals the old S0 and G is unchanged. Each `SnapshotFetch` returns exactly one `RecoverySnapshotChunk` in its correlated `RpcResult`, associated only when its boundary bytes equal S0. `RecoverySnapshotComplete` records local transfer completion derived from complete index coverage and bounded byte accounting; the protocol defines NO wire transmission for it (no method, no result slot, and no `RecoveryNotification` arm). Installation is application-local durable replacement under S0: it does not rebase the shared provider stream, does not change G, and subsequent batches for that subscription chain from S0 within the same G, while unrelated subscribers continue from their own checkpoints. The snapshot live gate is separate from the subscribe-B gate: old replay completions cannot release snapshot-held batches; the initiator opens the snapshot live gate only after a validated `RecoverySnapshotInstalled` matching H, G, and S0, and any later catch-up round after installation obtains a fresh H and B. A provider needing a genuine shared rebase performs and signals it before issuing a descriptor in the new generation; an install confirmation never creates that rebase. Before descriptor exposure the provider and host coordinate a recoverable binding of S0 to `(P, S, G)` and the snapshot contents, resumable with host validation even if the initiator durably installs then loses SnapshotConfirm or its response, independent of per-handle reply caching; loss of that binding requires explicit reporting and snapshot fallback or scoped generation invalidation, never reinterpretation of old S0 in a new G. Snapshot formats remain provider-defined. Syntra defines only the transfer, boundary, and confirmation mechanics.

**SYN-URP-017** — The host MUST route every batch to exactly one targeted delivery instance by its current handle, MUST terminate only the targeted subscription on per-stream termination with a typed terminal signal inside a profile payload or invocation error where possible, MUST NOT end the connection to terminate one stream except where the connection itself ends, and MUST keep connection state for ACTIVE and CLOSING, principal binding, and confirmed capabilities separate from per-instance state for handle H, current round, generation, checkpoint bindings, catch-up phase, held queue, and routing entry.

**SYN-URP-018** — The host MUST bound all profile resources and document every bound: maximum subscriptions per connection and per principal, maximum pending profile invocations per connection, maximum queued `Notification` bytes per stream and per connection, maximum replay page batches and bytes, maximum snapshot page bytes and total pages, and effective deadlines for profile invocations. Saturation of a subscriber's delivery or holding queue is subscriber-local: the host MUST end the affected subscription with the mutually exclusive `terminated=true` outcome at the CURRENT generation and a non-empty, machine-readable ASCII `terminate_reason` denoting local queue exhaustion — `local-queue-exhausted` — and MUST NOT select `next_generation` there; an affected pending profile invocation MAY also fail with `RESOURCE_EXHAUSTED`. Rejecting new work before an overflowed subscription is accepted remains a valid policy (`RESOURCE_EXHAUSTED` with documented backoff). A bare reject-new-work response is insufficient once an already accepted subscription can no longer reach completion: that subscription MUST become explicitly recovery-needed/terminated. If even the terminal control signal cannot be queued, the host MUST reserve bounded control capacity or close the exhausted connection explicitly; it never leaves a silently live or stalled subscription. A genuinely exhausted connection has connection scope but still does not change provider G merely because its queues filled; true history loss is handled per SYN-URP-012. Unbounded queueing and silent deadlock are forbidden.

**SYN-URP-019** — The host MUST authorize the bound principal at every profile authorization hook: subscribe, replay, snapshot offer and transfer, and continuation, catch-up, and confirm. The host MUST NOT emit batches for a revoked or expired principal and MUST deny the affected principal at every hook with targeted termination where possible, never a reset of unrelated principals' streams. Revocation alone is targeted termination; if policy also invalidates that principal's recovery history the host changes only that scoped generation (or rejects that scoped binding) and explicitly invalidates its checkpoints. Regrant never revives an invalidated binding. Other principals observing the same underlying source keep their own valid bindings and subscriptions. Credential bytes MUST be treated as opaque sensitive bytes: never logged, never persisted by the core, never placed in error detail.

**SYN-URP-020** — Negotiation-version enforcement: the host MUST select the maximum version it implements within the initiator offered range in `RecoveryNegotiateRequest`, MUST confirm only that selected version in `RecoveryNegotiateResponse`, and MUST fail no overlap with `FAILED_PRECONDITION` in `RpcResult`. Both peers MUST carry the confirmed `profile_version` on every other profile payload; mismatch or missing version MUST fail with `FAILED_PRECONDITION`.

**SYN-URP-021** — Unknown-field/profile handling consistent with `specifications/core/serialization.md` (`SNTR-SER-003`) and `specifications/core/versioning.md` (`SNTR-VER-004`): unknown Protobuf fields inside profile payloads MUST be ignored on receipt unless explicitly marked `Critical` in `proto/syntra/v1/recovery_profile.proto`; fields explicitly marked `Ignorable` MUST be ignored; unknown profile operations MUST be rejected with `UNIMPLEMENTED`. A wire carrier for `RecoverySnapshotComplete` is not a profile operation and has no designated method, result slot, or `RecoveryNotification` arm; transporting one is an unknown/unregistered shape and MUST NOT be treated as snapshot completion. Emptiness is per-field, not blanket (missing/mismatched where non-empty is required MUST fail with `FAILED_PRECONDITION`, never silently applied):

| Field | Rule | Empty sentinel meaning |
|---|---|---|
| `profile_version`, `min_version`/`max_version`, `capability` | MUST be non-empty/valid | No empty form; missing or invalid → `FAILED_PRECONDITION` |
| `stream_selector`, `subscription_handle`, `snapshot_handle` (where required) | MUST be non-empty | No empty form; missing → `FAILED_PRECONDITION` |
| `start_checkpoint` | MAY be empty | Empty means initial subscription; non-empty resumes from the durable known-safe checkpoint (SYN-URP-005/024) |
| `continuation_marker` | MAY be empty | Empty means first replay request or no further page (SYN-URP-022) |
| `terminate_reason` | MAY be empty | Empty means no termination; non-empty required only when the terminated outcome is selected (SYN-URP-018/026) |
| `predecessor_checkpoint`, `result_checkpoint`, `boundary_checkpoint`, `catchup_boundary`, `live_boundary_checkpoint` | Per field comment | Presence/pairing governed by SYN-URP-013/023/024; `catchup_boundary` in subscribe response MUST be non-empty (SYN-URP-023) |

**SYN-URP-022** — Replay continuation echo, exact retry, and round fencing: replay applies only to resumption from a non-empty `start_checkpoint`. When subscribe used an empty `start_checkpoint` (initial subscription) the initiator MUST NOT send `RecoveryReplayRequest` and MUST obtain its live baseline at B by CatchUp or live validation (SYN-URP-024). For resumption, the initiator MUST send an empty `continuation_marker` on the first replay request with `from_checkpoint` set to its durable known-safe checkpoint C (non-empty; per §7, C may be newer than the last peer-acknowledged checkpoint but is never fabricated), and MUST echo the previous page's marker verbatim with `from_checkpoint` equal to the previous page's `result_checkpoint` on each continuation. The host MUST reject a mismatched marker or a non-chaining `from_checkpoint` with `FAILED_PRECONDITION`, except that the host MUST retain the last issued page per handle and generation and MUST return it verbatim without advancing on a duplicate of the immediately preceding completed request (identical payload in the current round), so unknown-outcome retries with fresh RPC request IDs stay safe. While the round remains current, loss of the completion signal is recovered only by bounded exact retries of the preceding request (or the same CatchUp request with fresh request IDs), for which the host returns the retained page/acceptance and re-emits that round's completion if already complete, without rerunning application effects, moving B, or restarting pagination. The host MUST clear the retained page on supersede, stream termination, later continuity change, or retention expiry; a timeout or retry-budget exhaustion on this path ends the round: the initiator retires H and starts a fresh round from durable known-safe C (SYN-URP-024). No same-handle second round and no marker reset is permitted.

**SYN-URP-023** — Subscribe boundary presence and completion gating: the host MUST return a non-empty `catchup_boundary` in the subscribe response, fixed at subscribe accept. Both peers MUST treat an empty boundary as omitted and MUST reject it with `FAILED_PRECONDITION`; the initiator MUST validate each `RecoveryReplayPage.catchup_boundary` and each completion-signal boundary (`RecoveryReplayComplete.live_boundary_checkpoint`, `RecoveryBatchTrailer.boundary_checkpoint` when `catchup_complete`, `RecoveryCatchUpAccepted.catchup_boundary`) against the subscribed boundary and MUST NOT release held live batches on mismatch; mismatch MUST be rejected with `FAILED_PRECONDITION` (or treated locally as recovery-needed) without releasing held batches. Held live batches are released only after all recovered data through B has passed validation and the local persistence gate and a completion matches the current connection, H, generation, profile version, and exact B; boundary equality alone never identifies a round. Retired-handle completions, pages, RPC results, and batches have no effect even when their B bytes equal the current B. Duplicate current completions with equal boundary bytes are idempotent and do not re-offer data; duplicate batch suppression follows version, handle/scope, generation, authorization, and bounds validation, and an already applied result checkpoint bypasses predecessor chaining only after that validation. The snapshot path is its own gate: old replay completions cannot release snapshot-held batches (SYN-URP-016).

**SYN-URP-024** — Round independence, second gap handling, and lost-completion exhaustion: every round begins with Subscribe and a fresh handle H and a newly captured non-empty fixed B. Initial subscriptions with an empty `start_checkpoint` skip Replay; CatchUp obtains an explicit baseline completion at B, and an initial live baseline does not assert installation of historical application state. A resumption carries the durable known-safe checkpoint C as `start_checkpoint` and replays per SYN-URP-022 while holding live batches until the validated completion at B. After durable progress C2 beyond B1, a new gap, loss-counter movement, or invalid completion starts a fresh round: the initiator retires H1 locally before new work — clears its held queue, cursors, and pending offers, requests Unsubscribe when possible — allocates H2 through Subscribe from C2, and the host captures B2 at that acceptance without waiting indefinitely for old teardown. A second gap is recovered toward B2, never replayed toward the obsolete B1; where C2 is no longer replayable, explicit snapshot fallback applies, never an empty-start silent restart. While a round stays current, a lost completion is recovered by bounded exact retries per SYN-URP-022; when the retry or deadline budget is exhausted the initiator retires H and starts a fresh round from durable known-safe C, requesting a fresh Subscribe rather than waiting indefinitely for teardown. The initiator MUST NOT treat idle as caught-up and MUST NOT release held batches without a validated completion signal; duplicate completions with equal boundary bytes are tolerated idempotently and mismatched completions never release held batches. Host resource bounds still apply; inability to retire remotely can require reconnect or backoff.

**SYN-URP-025** — Same-generation snapshot confirmation, supersede fencing, and stop-and-wait idempotency: snapshot installation is application-local and does not change the provider generation; `RecoverySnapshotInstalled` carries the unchanged current generation and the exact offered boundary S0, and subsequent checkpoints bind to that same generation. `SnapshotConfirm` uses the exact offered S0 and the current G; no separate replacement checkpoint field exists and no unseen post-install token may be inferred. The exact same-generation retry — an exact duplicate `RecoverySnapshotConfirmRequest` for the same authorized handle, version, current generation, and boundary bytes — MUST return the original retained `RecoverySnapshotInstalled` without reinstalling or any generation change, only while the response is retained, the generation is unchanged, and no supersede, termination, later scoped continuity change, or reply-cache expiry has ended eligibility. Equality of boundary bytes alone does not establish retry eligibility; on expiry or exhaustion the initiator uses the §7 reconnect path (fresh authenticated connection, re-negotiation, fresh H/B), never repeated installation, a fabricated pre-install-generation exception, or a manufactured generation change. Batch Confirm is idempotent with stop-and-wait fencing: re-presenting the same batch checkpoint bytes in the same generation MUST return `RecoveryConfirmResponse` without new side effects or generation change. A checkpoint never issued as committable for the handle and generation must fail with `FAILED_PRECONDITION` without advancing. Supersede, termination, later continuity change, or reply-cache expiry invalidates retained responses; protection, retention counts and lifetimes are deployment-documented. Gap, continuity-loss, and continuation-expiry reports invalidate any pending offer.

**SYN-URP-026** — Scoped invalidation, local saturation, and revocation split: a generation increment under SYN-URP-012 signals true provider history loss or an explicit shared rebase for the `(P, S)` scope, is signaled with a trailer carrying the old `generation` and the new `next_generation` with no second outcome selected, and invalidates prior-generation checkpoints across subscriptions for that scope. Subscriber-local saturation is not such a change: it ends only the affected subscription with `terminated=true`, the current generation, and ASCII `terminate_reason = local-queue-exhausted`, never `next_generation`; an initiator cannot manufacture a provider `next_generation` (SYN-URP-007). A retention-window prune, per-stream terminal signal, connection end with explicit re-subscription under a fresh handle, offer or persist failure, confirm retry, or batch validation failure also does not change G beyond the scoped rules above. Revocation behavior follows SYN-URP-019: targeted termination always, scoped generation change only under an explicit history-reset policy. The host MUST NOT leak other principals' stream state or place credentials in error detail.

## 3. Stream identity, delivery instance, handle, and rounds

A subscription is established only by generic invocation after ACTIVE and is one delivery instance routed by a fresh connection-scoped handle. Stream identity S is resolved by the provider from the selector within principal scope P and persists across subscriptions and connections; several delivery instances MAY observe the same S with independent queues, phases, and generations. Identical selector bytes do not establish identical resolved S, scope, or authority.

The opaque handle is returned inside `RpcResult` payload and is carried inside each profile batch payload so the initiator can route to exactly one delivery instance. The core does not interpret the handle. Handles are connection-scoped; a new subscription yields a new handle; a retired handle is never reused within a connection, and all handles are discarded at connection end. Delivery begins only after host confirmation. The handle authorizes nothing by itself.

A round is identified by `connection + H`, holds one immutable boundary B captured at accept, and runs Replay or CatchUp, never both concurrently. A newly captured B may equal a previous round's boundary where no source progress occurred; equality never identifies a round. When a round ends abnormally — new gap, loss-counter movement, invalid completion, or local saturation — the initiator retires H locally: clear its held queue, cursors, and pending offers, best-effort Unsubscribe, then Subscribe again for the next handle without waiting indefinitely for its confirmations; retired-handle completions, pages, RPC results, and batches have no effect even when their boundary bytes equal the current B.

Per-stream termination affects only the targeted delivery instance. Connection end discards all per-instance state. Re-establishment after connection end is always an explicit fresh authenticated connection, renegotiation, and re-subscription with a fresh handle and boundary, per SYN-URP-006. No stream survives its connection by default, consistent with [events](../core/events.md) session-loss behavior. Pending batches may still arrive after termination by race. Initiators tolerate post-termination batches.

## 4. Opaque checkpoint binding

Checkpoints are opaque bytes to Syntra. Initiators present exact bytes. Hosts bind bytes to exactly one `(P, S, G)` triple and validate the binding decisively; initiators persist the binding context with C without parsing C.

Each batch carries both a predecessor checkpoint and a result checkpoint. The predecessor states what the batch continues from. The result states what the batch advances to. Gaps are detectable by predecessor chaining without arithmetic. No peer computes a successor by increment or ordering inference. No peer parses checkpoint structure.

Forged, malformed, cross-stream, cross-generation, or cross-principal checkpoint bytes are rejected without leaking other principals' stream state. Checkpoints from a prior generation are rejected after a scoped generation change, never reinterpreted under the new generation. Checkpoints expire per documented retention and provider policy. Expired or outside-retention checkpoints resolve to the snapshot-required path with the binding otherwise unchanged; plain retention pruning neither increments G nor invalidates the checkpoint binding, distinguishing replay unavailability from binding invalidation.

Host validation of a resumable issued checkpoint is distinct from accepting an unoffered Confirm on an active handle: subject to the preconditions in SYN-URP-013, the host MAY accept valid C without a previous confirmation record, because locally durable and peer-acknowledged progress are separately tracked (§7). Confirmation proves only that the initiator application persisted the checkpoint through its persistence point. It never proves business success beyond what the provider specification states.

## 5. Replay paging and catch-up boundary

Replay is capability-gated. No replay exists unless negotiated under this profile. Where offered, replay is bounded paging, never unbounded burst.

Each replay invocation returns exactly one `RecoveryReplayPage` in its correlated `RpcResult`, stating its continuation marker and the round's fixed boundary B. The continuation marker states whether more pages remain; the initiator echoes it verbatim in the next replay request. Replay is sent only to resume from a non-empty `start_checkpoint`; initial subscriptions (empty `start_checkpoint`) skip replay and obtain their baseline completion at B by CatchUp (§5.2). The first replay request carries an empty marker with `from_checkpoint` set to the durable known-safe checkpoint (non-empty); each continuation carries the previous page marker with `from_checkpoint` equal to the previous page `result_checkpoint`. The host rejects a mismatched marker or a non-chaining `from_checkpoint` with `FAILED_PRECONDITION`, except for an idempotent duplicate of the immediately preceding completed request (identical payload in the current round), for which it returns the retained page verbatim without advancing (SYN-URP-022). The catch-up boundary states where recovered history meets live delivery. The initiator follows continuation markers page by page, stops at B, and validates each page and each completion-signal boundary against the subscribed B before releasing held live batches (SYN-URP-023).

Replay pages and statements are subject to the same queue bounds as live batches per [reliability](../core/reliability.md). Oversized history is paged across multiple bounded invocations. Invocation-triggered catch-up streams over the existing connection as `Notification` batches through the same validation and authorization path as live batches.

Recovered batches and live batches pass through the same validation pipeline: envelope validity, version match, handle/scope match, generation match, predecessor chaining, authorization context freshness, and size bounds. Duplicates across the recovered/live boundary are expected and tolerated only within a validated scope and generation. The initiator skips an already applied result checkpoint before predecessor chaining validation only after that validation; equal bytes from another connection, handle, generation, or principal context are never treated as a duplicate (SYN-URP-004).

Completion is explicit and fenced per SYN-URP-023. When the stream reaches live, the host emits an explicit catch-up completion signal matching the current connection, H, generation, version, and exact B. When the requested checkpoint is outside retention or otherwise unrecoverable by replay, the host fails the invocation with `FAILED_PRECONDITION` and emits the explicit snapshot-required signal without changing G. Silent truncation without the documented signal is forbidden.

```text
Initiator                              Host
    |                                     |
    |--- invocation{negotiate profile} --->|
    |<-- result{confirmed + bounds} -------|
    |--- invocation{subscribe generic,    |
    |         durable checkpoint C} ------>|
    |<-- result{handle H, generation G,   |
    |         fixed boundary B} -----------|
    |<-- notification{batch pending in    |
    |         held queue until completion}|
    |--- invocation{replay(from=C)} ------>|
    |<-- result{page 1, marker m1} --------|
    |--- invocation{replay(from=page1     |
    |         result, marker m1)} -------->|
    |<-- result{page 2, marker empty} ----|
    |<-- notification{replay_complete at  |
    |         B} --------------------------|
    |--- invocation{confirm checkpoint D}->|
    |<-- result{confirmed D} --------------|
```

### 5.1 Fixed-boundary round algorithm

The accepted algorithm, using only the terminology above and neutral mechanics only (generic subscription establishment, generic key/value read, echo round trip):

- Begin a round: the Initiator subscribes (from durable checkpoint C or empty), the Host resolves the scope `(P, S)`, allocates a fresh handle H, captures one non-empty fixed boundary B at accept, and returns the subscribe response inside its `RpcResult`. B never moves during the round.
- Hold live Batches: the Host pads the delivery instance queue with live Batches until the round release gate fires, so Batches emitted after subscribe accept are observable only after validated completion at B. Holding is bounded per SYN-URP-018; while held, saturation ends the subscription with `terminated=true` and ASCII `local-queue-exhausted` at the current generation and clears the held queue — never a bare `RESOURCE_EXHAUSTED` that would leave the stalled instance waiting for a completion signal it cannot reach, never a shared generation change. Outside holding, rejecting new work before acceptance remains valid with documented backoff.
- Replay through B one page per invocation: each Replay invocation returns exactly one page in its correlated `RpcResult` stating its continuation marker and B. Replay is sent only for resumption; initial subscriptions skip it. The first Replay carries an empty marker with `from_checkpoint` set to the durable known-safe checkpoint; each continuation echoes the previous marker verbatim with `from_checkpoint` equal to the previous `result_checkpoint`, and the Host rejects mismatch with `FAILED_PRECONDITION` except for an idempotent duplicate of the immediately preceding completed request, returned verbatim without advancing (SYN-URP-022). The Initiator follows the marker page by page and stops at B, validating each page boundary against B (SYN-URP-023). Oversized history is paged, never burst beyond documented bounds.
- Persist in order receive-validate-offer-persist-confirm: for each Batch through B, the Initiator follows the §7 sequence. The persist step covers the application effects represented by the checkpoint, atomically with `(P, S, G, C)` or under the declared idempotent recovery fence. Transport receipt or envelope decode is not reported as committed progress.
- Release gate at B: held live Batches are released only after all recovered data through B has passed validation plus the local persistence gate and a completion matches the current connection, H, generation, version, and exact B. After release the Host emits held then new live Batches chaining from B, and the Initiator validates them through the same pipeline. Duplicates across the recovered/live boundary are expected and tolerated within the validated scope only.
- Second gap and fresh rounds: after durable progress C2 beyond B1, a new gap retires H1 — clearing held queue and cursors — and a new round subscribes with `start_checkpoint=C2`, receiving a fresh H2 and a newly captured B2. Recovery runs toward B2, never toward the obsolete B1. Where C2 is no longer replayable, the snapshot-required signal is the explicit fallback; an empty-start silent restart is forbidden. Loss of completion inside a round is recovered by bounded exact retries; exhaustion retires H and starts a fresh round from durable known-safe C (SYN-URP-022/024).
- Snapshot fallback on outside-retention: when the requested checkpoint is outside retention or otherwise unrecoverable by replay, the Host fails the failing invocation with `FAILED_PRECONDITION` in `RpcResult` while emitting the explicit `snapshot_required=true` trailer in a `Notification` payload, without changing G. Recovery then follows the snapshot path with a provider-proven boundary S0 and the round restarts fresh after §6.
- Retirement and escalation: on new gap, loss-counter movement, invalid completion, or local saturation the Initiator retires H per §3, keeping protocol-fenced retired-handle results inert; a round never gets a second start under the same handle.

```text
Initiator                              Host
    |                                     |
    |--- invocation{subscribe generic,    |
    |         durable checkpoint C} ------>|
    |<-- result{handle H, gen G, fixed B} |
    |         (Host holds live Batches    |
    |          for this instance until    |
    |          completion at B; saturation |
    |          ends it with local-queue-  |
    |          exhausted at unchanged G)  |
    |--- invocation{replay from C} ------>|
    |<-- result{bounded page through B,   |
    |         continuation marker} -------|
    |<-- notification{replay_complete     |
    |         at B} ----------------------|
    |--- invocation{confirm checkpoint} ->|
    |<-- result{confirmed, same bytes} ---|
    |--- invocation{unsubscribe best-     |
    |         effort on gap; subscribe    |
    |         (start=C2)} --------------->|
    |<-- result{fresh handle H2, gen G,   |
    |         newly captured B2} ---------|
```

### 5.2 Round bootstrap, repeated rounds, and lost completion

SYN-URP-024 owns this subsection. An initial subscription carries an empty `start_checkpoint`, skips Replay entirely, and starts live at the subscribed boundary B on validated completion (or follows the snapshot path when `snapshot_required` is signaled); an initial live baseline does not assert installation of historical application state. A resumption carries a non-empty `start_checkpoint` equal to the durable known-safe checkpoint and replays per SYN-URP-022 while live batches are held until the validated completion at B. B is fixed at subscribe accept and never advances during paging; every page and every completion boundary is validated against the subscribed B per SYN-URP-023 before held batches are released.

Recovery rounds are independent and identified by `connection + H`: after a round completes, a later gap, loss-counter movement, timeout without completion, or boundary mismatch starts a new round from the durable known-safe checkpoint with a fresh handle and a newly captured boundary; the host captures the new boundary at that acceptance and never replays toward the obsolete boundary. The initiator never treats idle as caught-up and never releases held batches without a validated completion carrying equal boundary bytes and matching round identity. Duplicate completions with equal boundaries are tolerated idempotently; mismatched completions never release held batches.

A lost completion is not evidence of catch-up. While the round remains current the initiator repeats the exact preceding Replay request (or same CatchUp request) with fresh RPC request IDs under documented finite attempts, an absolute deadline, and backoff; the host returns the retained page or acceptance verbatim and re-emits that round's completion without rerunning application effects, moving B, or restarting pagination. On retry or deadline exhaustion the initiator retires H and starts a fresh round from durable known-safe C; a same-handle second round and a marker reset are never permitted.

## 6. Snapshot transfer and local installation

Snapshot is the fallback when replay cannot recover the requested checkpoint. It is also the only recovery when the durable checkpoint is outside retention. Formats are provider-defined. Syntra defines only transfer, boundary, and confirmation mechanics. Wire types are `RecoverySnapshotOfferRequest` / `RecoverySnapshotDescriptor`, `RecoverySnapshotFetchRequest` / `RecoverySnapshotChunk`, boundary confirm `RecoverySnapshotConfirmRequest` / `RecoverySnapshotInstalled`, and the `RecoveryNotification{trailer}` snapshot-required signal inside `Notification.payload`.

Offer: the host offers a snapshot under the provider-proven boundary S0 in response to `RecoverySnapshotOfferRequest` and binds the descriptor X to `(P, S, H, G, S0)`; the descriptor carries no generation field, and G is the established subscription generation. The boundary is proven by the provider, meaning the host application supplying the snapshot attests that subsequent batches chain from exactly that boundary within the current generation. At most one distinct X is offered under H: an exact duplicate offer under the active H returns the retained descriptor, and superseding an offer (gap, continuity-loss, or continuation-expiry reports invalidate any pending offer) retires H and requires a fresh Subscribe before a new X is issued — even when the new boundary equals the old S0 and the generation is unchanged.

Transfer: each `SnapshotFetch` returns exactly one `RecoverySnapshotChunk` in its correlated `RpcResult`, correlated by request ID, X, page index, version, and S0. Indices 0..N-1 are fetched exactly once logically; exact retries do not increase counts. A chunk is associated only when its `boundary_checkpoint` bytes equal S0; equality validates association only. Pages are bounded (`page_bytes_max`, `total_pages`); oversized snapshots are rejected without partial install, and a snapshot exceeding the maximum pages per offer requires a fresh round and a new offer after a fresh Subscribe. In-flight fetch under a superseded X or a retired handle fails with `FAILED_PRECONDITION`. Transfer completion is derived locally from complete index coverage and bounded byte accounting: the protocol defines NO wire transmission for `RecoverySnapshotComplete` (no method, no result slot, and no `RecoveryNotification` arm); its message types may describe a local transfer record only. Superseded X or mixed pages fail `FAILED_PRECONDITION`; the initiator discards staging and never partially activates it.

Installation: installation is application-local durable replacement of application state under S0, followed by `SnapshotConfirm` with the exact offered S0 and the current generation. It does not rebase the shared provider stream, does not change G, and produces no replacement checkpoint token: `RecoverySnapshotInstalled` carries the unchanged generation and S0. Subsequent batches for that subscription chain from S0 within the same generation and are rejected otherwise. Unrelated subscribers continue from their own checkpoints without reset. The initiator opens the snapshot live gate only after a validated `RecoverySnapshotInstalled` matching H, G, and S0; until then it holds live batches boundedly or proceeds per §7 reconnect after retry exhaustion, because a locally durable install alone is not a peer-acknowledged gate. The snapshot gate is separate from the subscribe-B gate: old replay completions cannot release snapshot-held batches, and any later catch-up round after installation obtains a fresh H and B. A provider needing a genuine shared rebase performs and signals it before issuing any descriptor in the new generation; an install confirmation never creates that rebase as a side effect, and an old S0 is never interpreted in a new G.

### 6.1 Confirm-retry fencing for snapshots

SYN-URP-025 owns this subsection. `SnapshotConfirm` uses the exact offered S0 and the current generation; success is `RecoverySnapshotInstalled{profile_version, subscription_handle, boundary_checkpoint=S0, generation=G}` — the unchanged current generation, with no replacement checkpoint field and no post-install token inferred. The retained-install retry is same-generation: an exact duplicate for the same authorized handle, version, current generation, and boundary bytes returns the original retained installed response without reinstalling or any generation change, only while the response is retained, the generation is unchanged, and no supersede, termination, later scoped continuity change, or reply-cache expiry has ended eligibility. Boundary equality alone does not establish retry eligibility. On retry or cache expiry the §7 reconnect path applies: the initiator durably installed S0, and reconnect verifies host validation of that issued binding (§2.2 SYN-URP-013) rather than fabricating a pre-install-generation exception or repeating installation. Retired-handle and superseded-offer confirms fail with `FAILED_PRECONDITION`.

Deployment documentation bounds retained responses by count, bytes, and lifetime; this profile defines no implicit minimum retry window. Confirmation stages remain distinct per §7: a locally installed snapshot and a peer-acknowledged install are different observations, and neither retroactively restores atomicity. This contract does not assert implementation coverage; execution evidence is tracked by the conformance suite, not this document.

```text
Initiator                              Host
    |                                     |
    |<-- notification{snapshot-required} --|
    |--- invocation{snapshot offer} ----->|
    |<-- result{descriptor(H, X, S0, N)} -|
    |--- invocation{fetch(X, 0)} -------->|
    |<-- result{chunk 0 @ S0} -------------|
    |--- invocation{fetch(X, 1)} -------->|
    |<-- result{chunk 1 @ S0} -------------|
    |         (transfer complete locally: |
    |          full index coverage; no    |
    |          wire RecoverySnapshot-     |
    |          Complete carrier exists)   |
    |   application-local install at S0,  |
    |         unchanged generation        |
    |--- invocation{SnapshotConfirm H,G,S0|
    |<-- result{installed(S0, G)} ---------|
    |<-- notification{batch chaining from |
    |         S0 in the same G} ----------|
```

## 7. Persistence, confirmation, and reconnect

The commit sequence receive → validate → offer → persist → confirm persists application effects, not merely checkpoint bytes:

1. Receive the batch over the existing connection.
2. Validate it through the same pipeline as live batches.
3. Offer it to the application above Syntra.
4. Persist the application effects represented by the checkpoint together with `(P, S, G, C)` atomically, or reconcile them under the declared idempotent recovery fence. A checkpoint ahead of durable application state is unsafe; application effects ahead of C may be replayed only with that fence, or recovered by a fresh local snapshot.
5. Confirm the checkpoint through the defined generic invocation.

Offer return, asynchronous write submission, decode, and transport receipt are NOT the durable success point. The application MUST declare its durable success point and fence contract, and unsupported persistence semantics cannot claim recovery safety. Syntra supplies neither a storage transaction nor exactly-once application effects; retries can repeat delivery, and crash safety comes from the application's atomic persistence or explicit idempotent recovery fence.

Three progress observations stay distinct and locally tracked (SYN-URP-006): **locally durable C**, **Confirm sent for C**, and **peer-acknowledged C** (a validated Confirm response). Sending does not acknowledge; acknowledging does not retroactively make local writes atomic. The durable known-safe C is the latest exact checkpoint whose represented application state and `(P, S, G)` binding are durable or reconcilable under the contract above; it MAY be newer than the last peer-acknowledged C after an acknowledgement is lost, and it is the value resumed from (§5.2, SYN-URP-022). Confirmation is stop-and-wait to bound pending state: the same method and exact payload MAY be retried with fresh RPC request IDs under documented finite attempts, an absolute deadline, and backoff. A late response for a retired handle does not advance the current round. Retry exhaustion leaves durable data intact and triggers reconnect and re-subscription — never rollback by guesswork, never infinite retry, and never an implicit acknowledgement.

Reconnect ALWAYS establishes a new authenticated connection, negotiates again, and subscribes with a fresh handle H and captured B. It transfers neither capability state nor pagination or snapshot handles. The recovering initiator supplies its durable known-safe C (or recovered snapshot boundary S0) as `start_checkpoint`, and the host validates the issued binding, current authority, binding consistency, and retention before resuming. Host validation of an issued checkpoint is distinct from accepting an unoffered Confirm on an active handle: batch Confirm still requires a committable batch result issued for that handle and generation, SnapshotConfirm the current offered boundary; subject to that, the host MAY accept valid C without a previous confirmation record (SYN-URP-013).

The durable-evidence reconnect matrix:

| Durable evidence on restart | Recovery action and host check |
|---|---|
| No durable application progress | Reconcile under the application fence and use the prior known-safe C where one exists; with none, make an explicit initial live-only baseline or snapshot choice per application intent. Initial live-only is never labeled as restored historical state. |
| Effects + C durable, Confirm never sent | Subscribe with C under the same `(P, S, G)`; the host validates the issued checkpoint and current authority, binding, and retention even though it never received Confirm. |
| Confirm sent, response lost, effects + C durable | Same re-subscription with C; no claim that the peer acknowledged. The host may accept valid C without a previous confirmation record. |
| Response received, acknowledgement bookkeeping lost | Durable C is still sufficient subject to host validation; a peer confirmation is not inferred to backfill missing durable application writes. |
| Snapshot + S0 durable, SnapshotConfirm or its response lost | Resume with exact S0 and the persisted `(P, S, G)` under the coordinated binding (§6); no obsolete X or H, and no generation inferred from an unreceived result. |
| Host restart/reply-cache expiry with provider history and binding intact | Validate C or S0 without the old handle's retry cache; capture a new B and resume. An expired same-handle retry is not required to succeed. |
| Same `(P, S, G)` but history outside replay retention | Explicit `FAILED_PRECONDITION` plus snapshot-required on the bound replay/catch-up path; no silent empty-start reset. |
| Provider loss or shared rebase changed G | Reject old C, explicitly invalidate scoped checkpoints (SYN-URP-012), then establish a current-generation subscription and snapshot. |
| Different P, different resolved S, revoked/expired authority, or invalid binding | Deny before effects or progress. No checkpoint transplant; reauthorization does not itself prove continuity. |

## 8. Flow control bounds

Every queue, page, transfer, pending count, and subscription count is bounded and documented per deployment. The accepted defaults recorded in the IDL and RFC 0006 §10: maximum 64 subscriptions per connection and 256 per principal; maximum 16 pending profile invocations per connection; maximum 256 KiB queued `Notification` bytes per stream and 1 MiB aggregate per connection; maximum replay page of 64 batches and 256 KiB, whichever binds first; maximum snapshot page of 256 KiB and 256 pages per offer; effective default deadline of 5 s for profile invocations where the invocation carries no explicit bounded deadline. Retention and reply-cache lifetimes are deployment-documented with no implicit minimum.

Initiators enforce pending-invocation, subscription, queued-byte, and page-size bounds and back off on `RESOURCE_EXHAUSTED`. Hosts enforce subscription, pending-invocation, queue-byte, page-byte, and deadline bounds and document every bound and default deadline.

On saturation the accepted policy applies ([RFC 0006 §11.4](../../rfcs/0006-update-recovery-profile.md#11-decision-amendment--release-inclusion-and-recovery-safety)): subscriber-local saturation is subscriber-local. Ending the affected subscription uses the mutually exclusive `terminated=true` outcome at the current generation with non-empty ASCII `terminate_reason = local-queue-exhausted` and never `next_generation`; an affected pending profile invocation MAY fail with `RESOURCE_EXHAUSTED`. While live batches are held during catch-up, saturation MUST end the affected subscription this way (held queue cleared) rather than leave it stalled waiting for an unreachable completion signal. Rejecting new work before a subscription is accepted remains valid (`RESOURCE_EXHAUSTED` with documented backoff). A genuinely exhausted connection is closed explicitly or given bounded reserved control capacity; a filled queue never changes provider G by itself. Unbounded queueing, silent deadlock, silent truncation, and initiator-manufactured `next_generation` values are forbidden. True shared history loss is handled per §2.2 and is separate.

Shutdown is orderly and explicit: stop new batches, observe the close grace, then tear down. In-flight profile invocations receive terminal errors. Connection interruption maps to `UNAVAILABLE` with unknown outcome for in-flight invocations, consistent with [reliability](../core/reliability.md).

## 9. Authorization hooks

Every profile operation is an authorization point for the bound principal: subscribe, replay, snapshot offer and transfer, continuation, catch-up, and confirm. Hosts re-evaluate the bound principal at each hook. Checkpoints, handles, and selectors are never authority by themselves.

Hosts do not emit batches for revoked or expired principals and deny the affected principal at every hook with targeted termination where possible (`RecoveryBatchTrailer{terminated=true}` with `terminate_reason` or a typed invocation error, plus `RecoveryUnsubscribeResponse` for explicit unsubscribe). Revocation alone never resets an unrelated principal's stream; it is targeted termination. Where policy additionally invalidates the principal's recovery history, the host changes only that scoped generation and explicitly invalidates that scoped binding's checkpoints, and regrant never revives an invalidated binding. Other principals observing the same underlying source keep their own valid bindings and subscriptions (SYN-URP-019/026).

Subscriber-local failures never change the generation: batch validation failure, offer or persist failure, confirm retry, per-stream terminal signal, local saturation, and connection end with explicit re-subscription under a fresh handle affect only the targeted delivery instance. Only true provider history loss or an explicit shared rebase changes the scoped generation and invalidates prior-generation checkpoints across subscriptions for the same `(P, S)` scope, with explicit trailer fencing (SYN-URP-012). Checkpoints from a prior generation are never reinterpreted under the new generation.

Credential bytes stay opaque sensitive bytes, presented only as defined by the handshake and any follow-up authentication payloads, transmitted only over secure transports in externally reachable deployments. The core does not log, persist, or interpret them. Error detail does not contain credentials, checkpoint secrets, or private provider diagnostics.

## 10. Error mappings

Profile errors use the existing typed codes. No code semantics change. Mappings:

| Condition | Code | Scope |
|---|---|---|
| Unknown profile operation | `UNIMPLEMENTED` | Affected invocation only |
| Use of an unconfirmed profile operation (profile not confirmed on this connection) | `UNIMPLEMENTED` | Affected invocation only |
| Unknown stream handle | `UNIMPLEMENTED` | Affected invocation on the handle, unless retained stale context is tracked (SYN-URP-024) |
| Use of an unconfirmed option on a connection that has confirmed the profile | `FAILED_PRECONDITION` | Affected invocation only |
| Unauthorized or unknown principal at any hook | `PERMISSION_DENIED` or `UNAUTHENTICATED` | Affected invocation and targeted termination where possible |
| Stale, forged, malformed, cross-stream, cross-generation, or cross-principal checkpoint | `FAILED_PRECONDITION`, or `UNAUTHENTICATED` where token-like | Affected invocation only, without leaking other principals' state |
| Requested checkpoint outside retention or unrecoverable by replay | `FAILED_PRECONDITION` in the failed replay/catch-up `RpcResult` plus explicit snapshot-required signal as `RecoveryBatchTrailer{snapshot_required=true}` in a `Notification` payload; no generation change | Affected stream, recovery by snapshot path with binding otherwise unchanged |
| Subscriber-local saturation of the affected delivery instance | `RESOURCE_EXHAUSTED` on affected pending invocation where applicable, plus targeted `RecoveryBatchTrailer{terminated=true}` at the CURRENT generation with `terminate_reason` `local-queue-exhausted`; never `next_generation` | Affected invocation or delivery instance only; other subscriptions unaffected |
| True provider history loss or explicit shared rebase | Explicit `RecoveryBatchTrailer` with old `generation` and new `next_generation`; subsequent old-generation operations fail `FAILED_PRECONDITION` | All subscriptions in the affected `(P, S)` scope only |
| Transport loss with invocations outstanding | `UNAVAILABLE` with unknown outcome | All in-flight invocations on that connection |
| Deadline expiry | `DEADLINE_EXCEEDED` | Affected invocation only |
| Per-stream terminal condition | Typed terminal signal inside a profile payload or invocation error where possible | Targeted delivery instance only, connection continues |

All bound violations are terminal for the affected invocation or delivery instance, not the connection, unless the connection itself is exhausted, violated, or revoked. Error detail carries no credentials or private diagnostics.

## 11. Capability negotiation and state separation

Negotiation is explicit generic invocation after ACTIVE. The initiator offers the identifier and payload version. The host confirms only the subset it implements for the bound principal. No handshake binding is used. Capability state is per connection and never transferred across connections; reconnection renegotiates (§7). Where the host does not confirm, peers operate mandatory-only or live-only generic subscription where separately agreed. The host does not silently weaken confirmation. The initiator does not proceed as if confirmed.

Connection state and per-instance state stay separate. Connection state holds ACTIVE and CLOSING phase, principal binding, and confirmed capabilities. Per-instance state holds handle H, current round identity, generation, checkpoint bindings `(P, S, G, C)`, catch-up phase, held queue, and routing entry. Per-instance termination and recovery-needed transitions never end the connection except where the connection itself ends.

Cancellation applies to the subscribing or profile invocation only and does not by itself terminate the stream unless the confirmed stream binding states so. Stream termination uses the targeted profile terminate operation or terminal signal. Every profile invocation has an effective deadline. Expiry surfaces as `DEADLINE_EXCEEDED`.

Ordering for one stream is generation-scoped send order on transports that preserve order, with predecessor and result chaining so gaps are detectable without arithmetic. No cross-stream ordering and no cross-connection ordering is claimed, consistent with [events](../core/events.md) ordering scope.

## 12. Compatibility and conformance notes

Wire impact is additive with zero envelope changes. Reserved values are preserved. Old and new peers interoperate mandatory-only. A confirming initiator against a non-confirming host falls back to mandatory-only plus any previously confirmed options and does not treat the absence as a connection failure where fallback exists.

Release inclusion ([RFC 0006 §11.1](../../rfcs/0006-update-recovery-profile.md#11-decision-amendment--release-inclusion-and-recovery-safety)) is a release obligation and does not alter claim selection here: recovery remains capability-gated under `SNTR-EVENTS-V1`, Core-only success cannot satisfy the recovery-inclusive release bundle, and a Core-only declaration reports recovery cases as SKIP/UNSUPPORTED, never PASS. Negotiated fallback outside the release target supplies no recovery guarantee and is recorded as such.
